# OWASP ZAP – Scanning Methodology

## 1. Objective

The objective of this assessment was to perform security reconnaissance and vulnerability assessment of a locally deployed OWASP Juice Shop application using OWASP ZAP.

## 2. Target

The assessment target was:

http://localhost:3000

The application was hosted locally using Docker.

## 3. Scope

Only the locally hosted Juice Shop application was considered in scope.

External domains and resources observed during browsing or scanning were excluded from vulnerability assessment conclusions.

## 4. Tools Used

- OWASP ZAP 2.17.0
- OWASP Juice Shop
- Docker
- Web browser
- Windows 11

## 5. Reconnaissance

The application was first accessed through the ZAP proxy.

Normal application traffic was generated by browsing the Juice Shop application.

ZAP recorded requests and responses in its Sites tree and History.

## 6. Client Spider

The ZAP Client Spider was used to discover URLs and application resources within the local Juice Shop target.

The Client Spider identified application routes and resources that were subsequently available for security analysis.

## 7. Passive Scanning

ZAP's passive scanner analyzed requests and responses without actively modifying the application's behavior.

Passive findings included security-header issues, information disclosures, session-related observations, and other configuration findings.

## 8. Active Scanning

An active scan was performed against:

http://localhost:3000

The active scanner tested discovered application resources using ZAP's configured active-scan rules.

The scan identified a potential SQL Injection issue in:

`/rest/products/search`

with the vulnerable parameter:

`q`

## 9. Manual Validation

Selected findings were manually reviewed to distinguish automated alerts from findings supported by direct evidence.

The SQL Injection finding was manually validated using controlled input against the local Juice Shop instance.

The test:

`q=apple%27`

resulted in:

`HTTP/1.1 500 Internal Server Error`

The response contained an SQLite syntax error:

`SQLITE_ERROR: near "'%'": syntax error`

This was sufficient to classify the SQL Injection finding as confirmed for the assessment.

No destructive database operations or unauthorized data extraction were performed.

## 10. Alert Classification

Findings were considered using the following categories:

- Confirmed: supported by manual validation or direct evidence.
- Automated finding: reported by ZAP but not independently validated.
- Informational: provides application or scanning information rather than demonstrating a vulnerability.
- Out of scope: associated with an external resource rather than the local Juice Shop target.

## 11. Evidence

Evidence was collected from ZAP request/response information and alert details during the assessment.

The project maintains separate directories for:

- Requests
- Responses
- Screenshots

## 12. Limitations

This assessment was performed against a deliberately vulnerable local training application.

The results should not be interpreted as a complete security assessment of a production application.

Only the defined local target was considered within scope.

## 13. Assessment Flow

The overall workflow was:

Application Deployment
        ↓
ZAP Proxy Configuration
        ↓
Application Browsing
        ↓
Client Spider
        ↓
Passive Scanning
        ↓
Active Scanning
        ↓
Alert Review
        ↓
Manual Validation
        ↓
Vulnerability Analysis
        ↓
Remediation Recommendations
